Test helpers:
- `createTestUser(overrides?)`: creates user with hashed password, role defaults to 'MEMBER'
- `getAuthToken(userId)`: signAccessToken for the user, create session
- `createTestCredentialDirect(createdById, overrides?)`: use encrypt() from crypto.ts to create credential directly in DB (bypassing API), then grantCredentialAccess to creator with MANAGE

CRITICAL: encrypt() is SYNCHRONOUS. Do NOT await it. decrypt() takes an EncryptedData object.

Test groups:

**POST /api/credentials (CRED-01, CRED-06)**
- 201: creates credential, response has { credential } with id/friendlyName/systemHost/username/expiresAt/createdById/createdAt/updatedAt
- 201: response does NOT contain secret, encryptedValue, iv, authTag, keyVersion (check all five are undefined)
- 201: database row has encryptedValue that is NOT the plaintext secret (query raw, compare)
- 201: creator automatically has MANAGE access (check credentialAccess table)
- 201: with expiresAt field set (CRED-06)
- 400: missing required fields (no friendlyName)
- 401: no auth token

**GET /api/credentials (CRED-03 list scoping)**
- 200: SUPER_ADMIN sees all credentials
- 200: MEMBER sees only credentials they have access to (create 2 creds, grant access to 1, expect list length 1)
- 200: response items have no encrypted fields

**GET /api/credentials/:id (CRED-03)**
- 200: user with VIEW access gets credential
- 200: response has no encrypted fields
- 403: user without access gets ForbiddenError
- 404: deleted credential returns not found

**PATCH /api/credentials/:id (CRED-05)**
- 200: user with EDIT access can update friendlyName
- 200: update with new secret re-encrypts (read DB before and after, encryptedValue differs)
- 200: update without secret field leaves encryptedValue/iv/authTag unchanged in DB
- 200: can set expiresAt, can clear expiresAt to null (CRED-06)
- 403: user with VIEW-only access gets 403
- 400: empty body (no fields provided)

**DELETE /api/credentials/:id (CRED-05)**
- 204: user with MANAGE access can delete
- After delete: GET returns 404, credential no longer in list
- 403: user with EDIT access cannot delete (requires MANAGE)

**POST /api/credentials/:id/reveal (CRED-04)**
- 200: returns { secret } with the original plaintext value
- 200: creates audit log entry with action 'REVEAL', targetType 'CREDENTIAL', targetId matching credential id
- 403: user without access gets 403
- 404: deleted credential returns not found

**Rate limiting (CRED-04)**
- 429: after 10 rapid reveal requests to same credential, 11th returns 429
- Note: use a loop of 11 requests. First 10 should be 200, 11th should be 429

**ACL enforcement across roles**
- SUPER_ADMIN can access any credential without explicit grant
- MANAGER can access any credential without explicit grant
- MEMBER without access gets 403 on all endpoints (get, update, delete, reveal)
